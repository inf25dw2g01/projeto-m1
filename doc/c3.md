# C3 : Product

## 3.1 Desenvolvimento

O projeto foi desenvolvido seguindo uma abordagem **API-first**: o ficheiro `openapi.yaml` foi definido primeiro e o **OpenAPI Generator** produziu automaticamente a estrutura base do servidor Express (controllers, services, router e validador). A partir desta base gerada, a lógica de negócio, os modelos Sequelize e a camada de autenticação foram implementados manualmente.

### Tecnologias utilizadas

| Tecnologia | Função |
|------------|--------|
| Node.js | Runtime do servidor |
| Express | Framework HTTP |
| Sequelize | ORM para MySQL |
| MySQL | Base de dados relacional |
| Passport.js | Gestão de autenticação |
| express-openapi-validator | Validação automática de req/res |
| helmet | Segurança de headers HTTP |
| express-rate-limit | Proteção contra DoS/força bruta |
| Docker / Docker Compose | Containerização multi-serviço |

## 3.2 Instalação

### Pré-requisitos

- [Docker Desktop](https://www.docker.com/products/docker-desktop/) instalado e em execução
- Git

### Passos

**1. Clonar o repositório**

```bash
git clone https://github.com/inf25dw2g01/<repo>.git
cd <repo>
```

**2. Arrancar em produção**

docker compose -f src/docker-compose.prod.yaml up --build

A aplicação fica disponível em `http://localhost:8080`.

**3. Arrancar em desenvolvimento** (com hot-reload)

- através do comando 'npm start' dentro da pasta /src/express-server

## 3.3 Utilização

### Portal Web

Acede a `http://localhost:8080` para usar o portal de autenticação. A página apresenta três métodos de entrada:

1. **Basic Auth** — email e password
2. **API Key** — cola a tua `x-api-key` no campo de validação
3. **Login Social** — GitHub, Google ou Discord via OAuth 2.0

Após o primeiro login OAuth ou Basic Auth, a API Key é gerada automaticamente e mostrada no perfil para o utilizador copiar.

### Documentação interativa (Swagger UI)

```
http://localhost:8080/api-docs
```

### Autenticação via API Key em pedidos diretos

```bash
curl -H "x-api-key: <a-tua-chave>" http://localhost:8080/users/me
```

## 3.5 Camada de Autenticação e Autorização

O projeto implementa uma arquitetura de autenticação híbrida onde todos os métodos convergem para o mesmo objeto: `req.user`. Independentemente do método usado, os controllers e services recebem sempre a mesma estrutura de dados.

### OAuth 2.0 — Authorization Code Flow

No callback de cada estratégia, o Sequelize verifica se o utilizador já existe pelo email (`findOrCreate`). Se for novo, regista-o na base de dados e gera automaticamente a sua API Key. A coluna `password` fica a `null` para utilizadores OAuth — medida de segurança que impede acesso via Basic Auth a contas criadas por redes sociais.


### API Key — Autenticação Stateless

A API Key é gerada automaticamente com `crypto.randomBytes(32).toString('hex')` no momento do primeiro registo e guardada na base de dados. Em cada pedido, o middleware `ApiKeyAuth.js` lê o header `x-api-key`, valida contra a base de dados e injeta o utilizador em `req.user` — sem criar sessão. Este método é **stateless** por design.

```javascript
// middleware/ApiKeyAuth.js
const user = await User.findOne({ where: { apiKey: apiKey } });
if (!user) return res.status(401).json({ error: 'API Key inválida' });
req.user = { id: user.id, firstName: user.firstName, ... };
```

### Basic Auth

Credenciais `email:password` enviadas em Base64 no header `Authorization`. O middleware `BasicAuth.js` descodifica, localiza o utilizador na base de dados e valida a password com bcrypt.

### Proteção de Infraestrutura

**Rate Limiting** — `express-rate-limit` limita a 100 pedidos por IP em janelas de 15 minutos nos endpoints `/api/`, protegendo contra ataques DoS e força bruta.

**Helmet** — configura automaticamente múltiplos headers de segurança HTTP (X-Frame-Options, X-Content-Type-Options, etc.). A diretiva `contentSecurityPolicy` foi desativada para permitir a execução de scripts inline pelo motor de views EJS, mantendo todas as restantes proteções ativas.
